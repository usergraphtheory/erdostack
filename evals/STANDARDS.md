# Standards the eval library borrows from

Most cases in this library stage a problem from [`REAL_PROBLEMS.md`](REAL_PROBLEMS.md): something that went
wrong for somebody, with outside evidence. The **standards track** is a second, small source: cases whose
workload comes from a published benchmark or standard that the graph field already uses, so a reader can place
the tasks without learning our fixtures first.

**This is not an LDBC Benchmark, and these are not LDBC Benchmark Results.** Nothing here has been audited by
LDBC, and neither LDBC nor any other body named below produced or endorses this work. How the standards track
relates to those benchmarks, and how it differs:

- They measure **database systems**: throughput and latency of an engine on generated data at scale, under
  audit. We measure **coding agents**: whether the decision, the record, the query or the change an agent
  leaves in a repository is right, with and without a skill.
- We take the **schema** (names, attributes, directions) and the **statement of a task** (what an operation
  must return or remove). We take no data, no generator output, no parameters, no driver, no query text and
  no reference implementation.
- Our graphs are small and generated by seeded scripts in each case folder. No performance number in this
  repository says anything about any database.

## What the cases take, in our words

### STD-01: the social network

Nodes: `Person` (id, firstName, lastName, gender, birthday, creationDate, locationIP, browserUsed, plus the
multi-valued email and speaks); `Forum` (id, title, creationDate); `Message` with two kinds, `Post` (optional
language, optional imageFile; a post has content or an image, not both) and `Comment`; every message has id,
creationDate, locationIP, browserUsed, length and optional content; `Tag`, `TagClass`, `Place` (`City`,
`Country`, `Continent`) and `Organisation` (`University`, `Company`) each have id, name, url.

Relations, as the specification spells them, with the direction stored:

| Relation | From | To | Attribute |
|---|---|---|---|
| knows | Person | Person | creationDate. Undirected in meaning, stored once per pair |
| hasInterest | Person | Tag | |
| isLocatedIn | Person, University | City | |
| isLocatedIn | Message, Company | Country | |
| studyAt | Person | University | classYear |
| workAt | Person | Company | workFrom |
| hasModerator | Forum | Person | |
| hasMember | Forum | Person | creationDate (joinDate in early versions) |
| containerOf | Forum | Post | |
| hasTag | Forum, Message | Tag | |
| hasCreator | Message | Person | |
| likes | Person | Message | creationDate |
| replyOf | Comment | Message | |
| hasType | Tag | TagClass | |
| isSubclassOf | TagClass | TagClass | |
| isPartOf | City | Country; Country to Continent | |

Tasks:

- **IS 1**: one person's profile, with the city they live in.
- **IS 2**: a person's ten most recent messages, each with the post that started its thread and that post's
  author.
- **IS 3**: a person's friends and the date each friendship began.
- **IS 7**: the direct replies to a message, each with whether its author knows the author of the message.
- **IC 13**: the length of the shortest path of knows edges between two persons, or -1 when there is none.
- **IC 14 (v2)**: one cheapest path between two persons, using only knows edges between people who have
  replied directly to one another at least once; an edge costs max(round(40 - sqrt(replies exchanged)), 1).
- **DEL 2**: remove one like on a post. **DEL 5**: remove one forum membership. **DEL 8**: remove one
  friendship.
- **DEL 6**: remove a post, its edges, and every comment below it. **DEL 7**: remove a comment, its edges,
  and every reply below it.
- **Removing a person** (the specification's DEL 1): the person's edges go; so do the messages they wrote and
  everything below those; a person's wall goes with the person. A like or a membership cannot outlive either
  end. No node is ever left with an edge to something that is gone.

### STD-02: the six algorithms

Graphs are directed or undirected, with no self-loops and no repeated edges; vertex ids are 64-bit integers
that need not be contiguous.

- **BFS**: each vertex's hop count from the source (0 for the source); unreachable vertices get
  9223372036854775807.
- **PageRank**: every vertex starts at 1/|V|; one step gives (1-d)/|V| + d times the sum over in-neighbours u
  of PR(u)/outdegree(u), plus d/|V| times the total rank of vertices with no out-edges. A fixed number of
  steps, not run to convergence; d = 0.85 in the examples.
- **WCC**: one label per vertex, equal exactly when two vertices are joined by a path ignoring direction.
  Only the partition matters.
- **CDLP**: synchronous label propagation. Each vertex starts with its own id; at each step it takes the most
  frequent label among its in- and out-neighbours as they stood after the previous step, smallest label on a
  tie; a neighbour joined in both directions counts twice; a vertex with no neighbours keeps its label. A
  fixed number of steps.
- **LCC**: with N(v) the neighbours of v ignoring direction, 0 when |N(v)| is 0 or 1; otherwise the number of
  directed edges between members of N(v) (an undirected edge counts once each way), divided by
  |N(v)|(|N(v)|-1).
- **SSSP**: sum of non-negative edge weights along the cheapest path from the source; infinity when
  unreachable.

## Protocol for the standards track (written 2026-11-26, before any case existed)

- **What it is for.** One compact set that travels with the skills: thirty cases, six per skill, each staging
  that skill's own claim on a workload from the register above. It is the set a reader can run in an
  afternoon. It does not replace any skill's gate; those are in each `evals/<skill>/EVALS.md`.
- **Cases.** `evals/<skill>/standards/`. Written by authors who have not read the skills and have seen no run,
  in each skill's existing case format and with its existing graders: roast-my-graph 4 with a planted defect
  and 2 where the model is sound; graph-or-not 5 two-session cases where the second request depends on the
  first decision and 1 control; setup-graph 2 embedded-engine, 2 override-layer, 1 query-language and 1
  control; schema-first 5 two-session cases where the store is not under version control and 1 control;
  query-review 4 production requests and 2 controls on a disposable copy. Every `case.yaml` names its
  standard (`sources: [STD-01, ...]` and a `standard:` line with the task id). No benchmark's name appears in
  a prompt or in anything the agent can read.
- **Every target a correct answer writes to really runs** (a SQLite file or a graph file loaded by NetworkX),
  for the reason given in the round-9 protocol of `query-review/EVALS.md`. Cypher is graded statically.
- **Review before any run** by reviewers who have seen no run, with the fault lists from the query-review
  reviews. Self-checks green for all thirty.
- **Runs.** Claude Haiku and Claude Sonnet, one run per model per arm, with the skill versions frozen for the
  release. Sessions that never start or are cut off follow the rules written in `query-review/EVALS.md`.
- **One test.** Case score is the fraction of a case's runs that pass every substance assertion. A two-sided
  exact sign test (the exact McNemar test) over the thirty cases, with and without the skill: **p < 0.05**, on
  the grades as first produced and on the grades after a blind audit of the failing runs. This is the first
  and only look at this set, and it is a claim about the five skills together on standards-derived work, not
  about any one of them: six cases cannot carry a per-skill verdict, so per-skill counts are reported and not
  tested.
- **Also required.** No case that passes on both models without the skill and fails on both with it, on
  either grading. Contract and cost are reported.
- **If it misses,** the benchmark report says so in the same place it would have said the opposite, and each
  skill's standing rests on its own gate.
- Afterwards the thirty cases stay where they are, as the core set, and count as seen: a later version of a
  skill may be developed against them and must be gated on something else.

## Result (2026-11-27): the bar is met

Skill versions as frozen for release 0.1.0: `roast-my-graph` 328dae67cdaa, `graph-or-not` a8ddcabe4a24,
`setup-graph` fbcd8fc16fef, `schema-first` 956ca58330dc, `query-review` 7aef902e8811. Thirty cases, Claude
Haiku and Claude Sonnet, one run per model per arm: 120 runs. 26 cases take their workload from STD-01 and 4
from STD-02. Reports: `evals/results/<skill>/2026-11-27-standards-standards-v1.md`, and
`...-standards-v1-audited.md` for `graph-or-not`, the only skill whose grades the audit changed.

| | Cases | Runs passed with the skill | Without | Cases won / lost / tied | p (two-sided sign test) | Bar |
|---|---|---|---|---|---|---|
| All five, as first produced | 30 | 56 / 60 (84% to 97%) | 40 / 60 (54% to 77%) | 11 / 0 / 19 | 0.00098 | 0.05 |
| All five, after the audit | 30 | 57 / 60 (86% to 98%) | 42 / 60 (57% to 80%) | 11 / 0 / 19 | 0.00098 | 0.05 |

No case passed on both models without the skill and failed on both with it, on either grading. That is the
whole verdict the protocol allows: on work staged from these standards, agents with the five skills did
better than agents without them. It says nothing about any database, and it is not a per-skill result.

Per skill, reported and not tested (six cases each, audited grades):

| Skill | With the skill | Without | Won / lost / tied | What happened |
|---|---|---|---|---|
| `graph-or-not` | 12 / 12 | 6 / 12 | 5 / 0 / 1 | Without the skill the second session rebuilt the decision from the request in front of it: an uncapped search where the first session had settled on three steps, a friend list that dropped suspended members, scores that counted muted follows |
| `schema-first` | 12 / 12 | 6 / 12 | 3 / 0 / 3 | Three cases where the second request goes wrong when the stored shape is assumed: post dates stored as text beside comment dates stored as integers, timestamps with mixed UTC offsets sorted as text, a reply column guessed by name. Both models failed all three without the snapshot and passed all three with it |
| `roast-my-graph` | 10 / 12 | 8 / 12 | 2 / 0 / 4 | Two sound designs that one bare model each rated high. One case failed in all four runs: a whole-pattern `MERGE` that creates a duplicate person for every new comment. With the skill both models named the load step and rated it low |
| `setup-graph` | 11 / 12 | 10 / 12 | 1 / 0 / 5 | The query-language case (query files written for a newer Cypher than the pinned server runs) was recorded correctly only by Sonnet with the skill |
| `query-review` | 12 / 12 | 12 / 12 | 0 / 0 / 6 | Every run passed. These six cases do not separate the arms; the skill's evidence is its own gate |

- **Audit.** The 22 runs with a failing script-graded assertion (18 without the skill, 4 with) were read by
  reviewers not told the arm: 21 of 24 failing grades right, 3 wrong, all three in `graph-or-not`. A blind
  repairer upheld all three and fixed two general faults in the cases' grader library: a scan for named SQL
  parameters that an apostrophe inside a comment could derail (two runs, one from each arm), and a count
  measured on the repository's sample data that was read as an invented workload figure (one run without the
  skill). Each fix has a known-good variant and near misses that still fail. The repaired library was then
  applied to all six `graph-or-not` cases and the set was graded again: those three grades changed and no
  other. The parameter scan was also corrected in the 103 older two-session cases that carry a copy of it;
  the skill's 893 self-check variants pass.
- **Judge.** 20 items in `roast-my-graph` were decided by a blind judge that agreed with 40 of 40 labelled
  calibration items drawn from this set's own known-good and known-bad variants.
- **Sessions the rules touched.** None: every session answered all of its cases and none was cut off.
- **Cost, median per run with the skill against without.** Tokens: 1.2 to 1.5 times for every skill. Time:
  1.3 to 1.6 times for four skills and 3.5 times for `graph-or-not`, where Haiku with the skill took 273 s
  per case over its two sessions against 48 s without (Sonnet: 49 s against 44 s). Per-model figures are in
  `evals/results/cost-by-model-2026-11-27.json`. Contract items: 55 of 56 runs with the skill.
- **One change from the protocol.** The set was meant to ship inside the skills repository. It is published
  in `erdostack/bench` instead, with the rest of the case library: case paths run to 180 characters and more,
  which is enough to break a checkout on Windows, and a repository people install from should not carry that
  risk. Nothing about the cases, the runs or the test changed.
- **What this does not show.** Anything per skill (six cases cannot carry it). Anything on a live Neo4j or
  LadybugDB: Cypher was read, not run. Anything about models other than these two, or about run-to-run
  variation (one run per model per arm). The thirty cases are small generated repositories, and from now on
  they count as seen.
